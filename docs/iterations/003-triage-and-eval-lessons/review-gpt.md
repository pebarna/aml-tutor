# Iteration 003 plan — consistency and flow review

1. **High — Signature consistency: Task 10’s `ARCHITECTURE.md` table changes two public parameter names.** The Global Constraints API list, Task 4 Interfaces, Task 4 reference code, and Task 5 calls consistently use `build_prompt(transaction, classifier_score, retrieved)` and `parse_triage_decision(tool_input, known_typology_ids)`. But Task 10 Step 2 proposes the Architecture row as `(transaction, score, retrieved) -> str / (tool_input, known_ids) -> dict` (`Task 10`, table snippet). That makes the final published API contract disagree with every earlier contract and implementation. The final table must retain `classifier_score` and `known_typology_ids` exactly.

2. **High — Forward-reference/contract gap: the lesson-015 full pipeline cannot supply `llm_judge_score`’s required `retrieved` argument.** `Task 8` defines `llm_judge_score(case, result, retrieved, *, client=None)`, while `Task 5` defines `triage(...) -> dict` whose reference implementation returns only `parse_triage_decision(...)`—`decision`, `rationale`, and `cited_typology_ids`; it does not return the retrieved typology list. Yet `Task 9` Step 5 tells the learner to run `triage(...)` per case, then call `llm_judge_score` per case, without specifying how to preserve or recompute the exact retrieved list. A learner following the stated sequence cannot construct the judge input from the prior result. The task must either make `triage` expose retrieval context, or explicitly prescribe the matching retrieval call and parameters before judging.

3. **High — Front-matter/definition-of-done contradiction: the plan promises no network-dependent baked-in test, but lesson 009’s test invokes a downloadable embedding model.** “Why these choices” says no baked-in test makes a network call (`Why these choices`, “No new `tutorial-engine` capability…”), and Definition of done says no baked-in test requires network access (`Definition of done`, third bullet). However, `Task 3` Step 4 runs `009_test_hybrid_retrieval.py`, whose tests call `top_k_typologies_hybrid`; its reference implementation constructs `SentenceTransformer("all-MiniLM-L6-v2")`, and the same step explicitly says the first run downloads model weights and requires network. On a clean machine the test therefore cannot meet the stated no-network definition of done. The plan needs a coherent policy—for example, inject/mock embeddings in the baked-in test, or narrow/remove the no-network claims.

4. **Medium — Task 1 does not enforce the 16-candidate invariant that later sections treat as guaranteed.** `Task 1` Interfaces and Step 4 expect a 16-line candidate file (8 fraud and 8 non-fraud), and `Task 6` repeatedly describes 16 candidates. But `build_eval_candidates.py` uses `n = min(N_PER_CLASS, len(fraud), len(non_fraud))`, so it can silently emit fewer than 16 rows whenever the committed fixture has fewer than eight examples of either class. Its printed output and Step 4’s expected text still claim 16. This is an internal Task 1 inconsistency and makes the lesson-012 narrative/count promise unreliable; the script should fail when either class has fewer than eight, or all downstream language should be made dynamic.

5. **Medium — The advertised default corpus-path behavior is not implemented by the Task 2 reference code.** Global Constraints and `Task 2` Step 5 say `corpus_path=None` resolves to `data/typologies.json` relative to the `aml-triage` root. But `Task 2` Step 3 sets `DEFAULT_CORPUS_PATH = "data/typologies.json"` and `_load_corpus` calls `open(corpus_path or DEFAULT_CORPUS_PATH)`, which resolves relative to the process cwd. The baked-in tests conceal this because each passes `corpus_path` explicitly. This is especially important because the plan explicitly distinguishes cwd-independent test paths from production defaults; the reference implementation cannot satisfy that production contract when called outside the project root.

6. **Low — The “At a regulated shop” completion criterion is a leftover/incomplete list.** Global Constraints require this paragraph in **every new spec** (`Global Constraints`, fourth bullet), and `Task 6` does in fact require one for lesson 012. But Definition of done’s corresponding bullet lists only 008, 009, 010, 011, 013, 014, and 015, omitting 012. The omission weakens the final completion check even though lesson 012 is part of the same new-spec set.

7. **No issue — Numbering consistency.** Lesson numbers 008–015 align across Task headers, intended spec/test filenames, stated JSON validation ids, ledger-row instructions, and the Task 10 Architecture-table rows. In particular, 008–011 remain Part 2 and 012–015 remain Part 3 as Task 10 specifies.

8. **No additional issue — Per-task spec/test/reference alignment.** Apart from the Task 1 candidate-count problem above and the Task 9 pipeline handoff problem above, each task’s described spec bullets match its shown baked-in test and scratch reference implementation closely enough for the requested consistency-and-flow scope.

9. **No issue — Lesson 012 cwd verification commands.** Task 6 correctly creates the scratch `aml-triage/data` directory, changes into that directory before both pytest executions, and invokes the test by absolute tutor-repo path. This matches `load_eval_set("data/triage_eval_set.jsonl")`’s process-cwd dependency. Task 10 appropriately excludes lesson 012 from its root-cwd batch and points back to Task 6 Step 5 for the separate verification.
